# 4.1.2 Name, Role, Value (Level A)

Canonical URL: https://www.w3.org/WAI/WCAG22/Understanding/name-role-value.html

For all user interface components, the name and role can be programmatically
determined; states, properties, and values can be programmatically set;
notification of changes to these items is available to user agents, including
assistive technologies.

## Why it matters

Custom components (tabs, carousels, modals, combo-boxes) often look the part
visually but are invisible to assistive technology because they lack roles,
names, and state. This is one of the most impactful gaps on modern sites.

## Common failures

- `<div>` used as a button with no role and no accessible name.
- Custom toggles with no `aria-pressed` / `aria-expanded` state.
- Icon buttons with no accessible name.
- Form fields whose value is not exposed to assistive technology when it
  changes dynamically.

## Fix guidance

- Prefer native HTML elements (`<button>`, `<input>`, `<select>`) when
  possible.
- For custom widgets, follow the ARIA Authoring Practices pattern for the
  role (tablist, dialog, combobox).
- Expose state via `aria-expanded`, `aria-pressed`, `aria-checked`, etc., and
  keep it in sync with the visual state.
- Give every interactive element an accessible name via visible text, `alt`,
  or `aria-label`.

- ARIA4: Using a WAI-ARIA role to expose the role of a user interface
  component.
- ARIA5: Using WAI-ARIA state and property attributes.
